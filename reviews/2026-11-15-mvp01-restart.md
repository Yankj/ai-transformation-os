# MVP-01 里程碑复盘：14 天闭环没有完成，2026-11-15 重启

## 原本要完成什么

MVP-01 的目标是：在 14 天内，围绕企业级 Agent Runtime 走完一条可重复的闭环——学习、沉淀知识卡、做出可复现的垂直切片、补上评测和演示，再写复盘并决定下一个主题。完成定义写在 [mvp-agent-runtime.md](../docs/strategy/mvp-agent-runtime.md)。

它要回答的问题不是「如何调用某个框架」，而是：怎样的 Runtime 才足够可靠、可观察、可演进。

## 心智模型上什么变了

启动时，切入点被放在 Agent Runtime，是因为「运行时契约」比框架更值得长期积累。这个判断仍然成立。

重启时更清楚的是另一件事：如果首屏只展示一份尚未执行的 14 天计划，仓库很难成为可被阅读的作品。与此同时，关于「谁来交付」以及「Docs / Rules / Skills 如何分层」的方法，已经足够写成公开知识卡，却一直留在仓库之外。先把这些方法脱敏后放进来，并不否定 Runtime 的重要性，只是不再假装 14 天冲刺还在进行。

也有一条没有变：没有可运行证据，就不把 Lab 或 Agent 写成已经完成。

## 摩擦和原因

能从公开记录确认的只有这些：

- 建仓后的 5 天，主要完成了操作系统和概念卡片，没有进入实验实现。
- 之后约四个月，本仓库没有新的提交；同一时期有其他公开产品与内容在推进。
- 因此中断首先表现为注意力没有回到这条闭环，而不是实现到一半被技术问题挡住。

本篇不补充未公开的工作原因，也不把其他仓库的进展计为 MVP-01 的完成项。

## 重启后的下一步

1. 发布 DP-001 与 AI-001，让仓库首先能被当作一份有主张的方法集来读。
2. 保持 Agent Runtime Lab 为「已设计、未实现」。只有在准备写下第一段可测试代码时，才启动 Day 3–4 的实现，而不是补一份看起来已经跑通的说明。
3. 若重新启动 Lab，仍遵守原范围：一个场景、一个 Agent、一到两个工具、先用确定性的假模型，再考虑真实模型接入。
4. 在 Lab 跑出第一条可复现的失败路径之前，不把相关内容 brief 写成可发布文章。

## 一次承诺

下一次和本仓库有关的公开更新，要么是对这两张新知识卡的修正，要么是 Lab 的第一段可测试实现；不再只增加新的计划文档。
