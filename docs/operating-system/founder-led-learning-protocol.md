# 创始人主导学习协议 / Founder-led learning protocol

## 决策 / Decision

ATOS 的学习不采用"AI 先写文档、创始人再阅读"的模式。创始人先从一手资料中形
成自己的理解并完成最小实践；AI 以教练、架构师和编辑的角色，通过追问、挑战、证据
校验和结构化归档，帮助理解成为可复用资产。

The founder learns from primary material and performs a minimal practice first.
AI acts as coach, architect, and editor—not as a substitute for earned understanding.

## 每日学习流程 / Daily learning flow

每个学习主题（如 Day 1）经历以下 6 个阶段。AI 在每个阶段有不同的角色，每个阶段
都有明确的进入条件和退出条件。**未经双方确认，不会跳过任何阶段。**

```
Phase 1: 学习启动   → AI: 引导者     (Guide)
Phase 2: 概念考察   → AI: 考官       (Examiner)
Phase 3: 实践演练   → AI: 教练       (Coach)
Phase 4: 总结思考   → AI: 合伙人     (Partner)
Phase 5: 知识整理   → AI: 编辑       (Editor)
Phase 6: 自媒体化   → AI: 策展人     (Curator)
```

### Phase 1: 学习启动 / Learning Launch

**AI 做什么：**
- 给出当天的学习问题（来自 syllabus）
- 推荐一手资料来源（官方文档、SDK 源码、厂商工程文章）
- 设定最小实践任务和停止条件

**创始人做什么：**
- 查阅资料，形成自己的理解
- 完成最小实践（画图、写伪代码、推演场景）
- 用交接格式提交学习成果

**进入条件：**上一阶段的复盘结论已确认。
**退出条件：**创始人提交了交接格式，AI 确认收到完整信息。

### Phase 2: 概念考察 / Concept Examination

**AI 做什么：**
- 基于创始人的理解，提出最多 3 个追问
- 追问聚焦于：机制解释、边界条件、反例/失败路径
- 判断是否达标

**创始人做什么：**
- 用自己的话回答问题
- 如果答不出，补充学习后再回答

**进入条件：**Phase 1 退出条件已满足。
**退出条件：**
- 达标 → 进入 Phase 3
- 不达标 → AI 继续追问或要求补充学习，直到创始人能用自己的话解释清楚

**不达标时的处理：**AI 不进入下一阶段，而是指出理解中的模糊点，建议补充学习
来源或重新审视某个概念。

### Phase 3: 实践演练 / Practice Exercise

**AI 做什么：**
- 设计一个最小实验，验证 Phase 2 的结论
- 挑战失败路径和边界情况

**创始人做什么：**
- 动手做实验（画图、写代码、运行推演、修改 Lab）
- 提交实践产物（代码链接、图片、可复现的步骤）

**进入条件：**Phase 2 达标。
**退出条件：**AI 评审实践产物，确认实验覆盖了学习问题的核心验证点。

### Phase 4: 总结思考 / Reflection

**AI 和创始人共同做什么：**
- 复盘：今天验证了什么结论、推翻了什么直觉
- 识别：当前阻塞、内容种子、明天的唯一学习问题
- 填写每日复盘模板

**进入条件：**Phase 3 退出条件已满足。
**退出条件：**双方对复盘内容有共识。

### Phase 5: 知识整理 / Knowledge Assembly

**AI 做什么：**
- 将共识结论整理为候选知识卡或实验报告
- 确保符合模板结构和链接规范

**创始人做什么：**
- 审阅 AI 整理的草稿
- 确认或修改

**进入条件：**Phase 4 复盘完成。
**退出条件：**创始人发出"归档"指令。

**关键规则：**知识卡不会在创始人确认前写入 Git。未经"归档"指令的内容留在对话
或 `.local/` 临时区。

### Phase 6: 自媒体化 / Content Seed

**AI 做什么：**
- 提炼标题、受众、反直觉观点
- 生成内容 brief（article / video / talk 适配）

**创始人做什么：**
- 说出最值得帮助同行的一点
- 决定是否进入公开草稿

**进入条件：**Phase 5 归档完成。
**退出条件：**内容种子已创建（不强制发布）。

## 质量门控 / Quality gates

每个主题从 `draft` 进入 `validated` 必须满足：

1. 创始人能用自己的语言解释其机制和边界（Phase 2 考察通过）
2. 能在 Runtime Lab 中实现、观察或诊断一个相关行为（Phase 3 实践通过）
3. 能说明一个反例、失败路径或关键取舍（Phase 2 追问覆盖）

## 对话交接格式 / Session handoff

学习或实践后，创始人用下面格式把材料带回对话；不需要整理得完美：

```text
主题 / Topic:
来源 / Sources:
我自己的理解（最多 3 点）:
做了什么实践 / Evidence:
仍然不懂或不确定的点:
最值得输出的一点:
当前阶段 / Current phase: (1-6)
```

## 何时算学会 / What counts as learned

一个主题至少满足以下三项，才可从 `draft` 进入 `validated`：

1. 能用自己的语言解释其机制和边界；
2. 能在 Runtime Lab 中实现、观察或诊断一个相关行为；
3. 能说明一个反例、失败路径或关键取舍。

## 内容的质量门槛 / Content gate

每天都可产生一个**内容种子**，但只有具备真实工程证据的观点才进入公开草稿。禁止为
保持频率而发布未验证的总结。内容应优先回答"这如何帮助一位资深工程师做出更好的
工程决策？"。

## 每日复盘模板 / Daily review

```text
今天被验证的结论：
今天被推翻或修正的直觉：
实践证据：
当前阻塞：
内容种子：
明天唯一的学习问题：
是否归档：是 / 否
```

## AI 行为约束 / AI constraints

- **不替创始人学习。** 一手资料的查阅和理解必须由创始人完成。
- **不在 Phase 2 通过前进入 Phase 3。** 即使时间紧迫也不跳过考察。
- **追问不超过 3 个。** 聚焦于能改变理解质量的问题。
- **不提前归档。** 只在收到"归档"指令后更新 Markdown、索引和 Git。
- **标签区分事实与推断。** AI 的输出必须标明哪些是创始人已确认的事实、
  哪些是 AI 的推断或假设。
- **范围守卫。** 发现范围漂移时，主动提醒并建议记录到 parking-lot.md。
